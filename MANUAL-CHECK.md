# Ручная проверка Дня 18 в браузере

Сценарий для проверки руками: у агента есть планировщик фоновых заданий. Задание
— это «какой инструмент MCP вызвать, с какими аргументами и когда»; выполняет
задания отдельный процесс-работник; накопленное видно в сводке, и свежую сводку
агент показывает сам, без вопроса о ней.

Каждый шаг устроен одинаково: **что сделать** → **что должно получиться**.

Время: около 30 минут. Вызовов модели: 3–5. В шапке выберите модель
**DeepSeek V4 Flash (ds-flash)**: она отвечает быстро и уверенно пользуется
инструментами.

Сценарий пройден в браузере (headless Chrome, порт 5001) на живом моке трекера,
живом работнике и живой модели: ожидания ниже — то, что происходит на самом
деле, включая время ожидания.

---

## Часть 0. Подготовка

Понадобятся **три терминала**: страница, мок-трекер и работник. Это не
усложнение ради проверки — так планировщик и живёт: работник должен пережить
закрытие страницы.

```bash
# терминал 1 — страница
cd ~/Документы/AI-Advent-Challenge/Day-18
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt     # Flask, httpx и MCP SDK (mcp 2.x)
cp -n .env.example .env                       # если .env ещё нет
mv memory memory-до-проверки 2>/dev/null || true
.venv/bin/python web.py
```

```bash
# терминал 2 — API, вокруг которого построен инструмент Дня 17
cd ~/Документы/AI-Advent-Challenge/Day-18
.venv/bin/python tracker_api.py --сброс       # 127.0.0.1:8766, данные заново
```

Работника пока **не запускайте**: первая часть проверяет, что без него задания
просто ждут и что страница об этом честно говорит.

Системный `python3` не подойдёт: в нём нет ни Flask, ни MCP SDK. Для серверов
`filesystem` и `everything` нужен Node.js 18+ (`node --version`); чтобы не ждать
посреди проверки, прогрейте кэш `npx` заранее:

```bash
npx -y @modelcontextprotocol/server-everything --help < /dev/null
npx -y @modelcontextprotocol/server-filesystem /tmp < /dev/null
```

Откройте <http://127.0.0.1:5000> (или тот порт, что напечатал `web.py`).

- [ ] Заголовок страницы: «Агент миграции ГИС — планировщик и фоновые задачи».
- [ ] Справа — панель **Планировщик**, и она появилась сама, без нажатий.

- [ ] В строке инструментов — цена: «схема ≈ 1 510 ток. в каждом запросе».

## Часть 4. Сводка — агрегированный результат

**4.1.** Нажмите **Собрать сводку** в панели.

- [ ] Системная строка «Сводка №1 собрана».
- [ ] В панели появился раскрывающийся блок «Сводка №1 от …». Раскройте:
      «запусков N, сбоев 0, пропусков 0», строки по заданиям, напоминание.

**4.2.** Измените данные в трекере мимо агента — так, как это сделал бы
коллега. Во втором терминале:

```bash
curl -s -X POST -H "Authorization: OAuth mock-token" -H "X-Cloud-Org-ID: mock-org" \
     -H "Content-Type: application/json" \
     http://127.0.0.1:8766/v3/issues/MIG-2/transitions/start_progress/_execute -d '{}'
```

(Точный идентификатор перехода показывает
`curl -s -H "Authorization: OAuth mock-token" -H "X-Cloud-Org-ID: mock-org" \
http://127.0.0.1:8766/v3/issues/MIG-2/transitions` — возьмите любой доступный.)

**4.3.** Дождитесь, пока задание `tracker__list_issues` сработает дважды —
или поставьте его заново с расписанием `каждые 30с`, чтобы не ждать полчаса.
Затем нажмите **Собрать сводку** ещё раз и раскройте её.

- [ ] Среди строк — само изменение словами, например
      «задачи[MIG-2].статус: Открыта → В работе» и «найдено: 8 → 9», если
      задача появилась.
- [ ] Это и есть периодический сбор данных: агрегируется не «сколько раз
      позвали», а что изменилось между краями окна.

**4.4.** Поставьте сводку на расписание: инструмент `scheduler__build_digest`,
когда `ежедневно в 09:00` (или `каждые 5м`, чтобы увидеть сегодня).

- [ ] Карточка задания с этим расписанием появилась.
- [ ] Когда оно сработает, у сводки появится связный абзац текста — его пишет

- [ ] При ближайшем ответе агента в переписке появится «📋 Свежая сводка №…» —

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| панель говорит «Работник не запущен», хотя терминал открыт | работник запущен с другим каталогом памяти: он и страница должны видеть один `memory/scheduler.db`. Сверьте путь в выводе `worker.py --состояние` |
| задание стоит, срок прошёл, а запусков нет | работник не запущен либо опоздал больше окна (`--опоздание`): смотрите `python cli.py --запуски` — там будет отметка «пропуск» |
| у сводки только цифры, текста нет | работник запущен с `--без-модели` или провайдер не ответил. Цифры важнее текста, поэтому сводка остаётся |
| «Не понял расписание …» | расписание пишется словами: «через 15м», «каждые 30м», «ежедневно в 09:00», «в 18:30» |
| в заявке на `schedule_job` непонятно, что будет вызвано | смотрите аргумент `tool` в карточке заявки: именно он определяет, нужна ли заявка |
| `ModuleNotFoundError: No module named 'flask'` или `'mcp'` | запущен системный `python3` — запускайте `.venv/bin/python` |
| «Трекер не отвечает по адресу http://127.0.0.1:8766» | не поднят мок: `.venv/bin/python tracker_api.py` во втором терминале |
| «Трекер не принял токен (401)» | мок запущен со своим `--токен`; верните значение по умолчанию или задайте `TRACKER_MOCK_TOKEN` в `.env` |
| `tracker-real` не показывает `add_comment` | так и задумано: у настоящего Трекера запись включается `TRACKER_WRITE=1` |
| карточек MCP нет, есть красная «Файл … — не JSON» | в `mcp-servers.json` синтаксическая ошибка — `git checkout mcp-servers.json` |
